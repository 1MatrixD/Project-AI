# Проекты ИИ

[![CI](https://github.com/1MatrixD/Project-AI/actions/workflows/ci.yml/badge.svg)](https://github.com/1MatrixD/Project-AI/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

Self-hosted система «второй мозг проекта»: детальная карта знаний кодовой базы в Neo4j,
чат с ИИ (Claude Code headless), канбан задач, обработка материалов (созвоны, ТЗ,
документы) и генерация плагинов Claude Code для каждого проекта.

*English version: [README.md](README.md).*

## Зачем

Работа с ИИ-агентом над реальным проектом каждый раз ломается в одном месте: агент не знает
кодовую базу, поэтому либо читает половину репозитория в контекст, либо угадывает. А настоящее
знание живёт в созвонах, ТЗ и решениях, которые никто не записал туда, где агент их увидит.

«Проекты ИИ» встают между командой и кодом:

- **Карта знаний вместо контекстного окна.** Каждый файл один раз разбирается ИИ (роль,
  выжимка, сущности, связи) и ложится в граф. Вопросы идут сначала в граф, потом в код.
- **RLM (Recursive Language Models) для больших кодовых баз.** Корневой агент выбирает по карте
  группы файлов, изолированные под-агенты читают только свою группу, корень сводит ответ.
  Под-агент может задать уточняющие вопросы и породить свой слой. Весь репозиторий не читает никто.
- **Досье, а не решение.** Строка с созвона («промик не применяется на сайте») превращается
  в досье по реальному коду: как понята задача, гипотеза с уверенностью, *где смотреть* и что
  там проверить, образец рядом, *нюансы* — что заденет правка, *как проверить* и развилки,
  которые должен решить человек. Как делать — решает исполнитель, человек или агент.
- **Соглашения — полноправная сущность.** «Роль ORGANIZER упразднена, теперь MANAGER + права»
  записывается один раз и попадает в каждую проработку — остатки старого подхода не заводятся как баги.
- **Карта возвращается в Claude Code.** Для каждого проекта генерируется плагин: MCP-сервер
  с картой знаний, канбаном и RLM-инструментами плюс скиллы (архитектура, бизнес-логика,
  рабочий процесс, разбор задач, как искать), которые пересобираются из карты при каждой индексации.

## Что умеет

- **Создание проекта** — указываешь каталог с кодом (кнопка «Обзор…» открывает
  системный диалог Windows), в фоне запускается анализ: структура, стек, ИИ-разбор
  каждого файла (роль, сущности, связи) → граф знаний Neo4j.
- **Дубликат проекта** — копия со всей картой знаний: файлы приезжают уже
  проанализированными, поэтому ИИ-разбор не запускается заново. Копия независима
  (свои строки в БД, свой подграф Neo4j, свои вектора) — удаление оригинала её не
  задевает. Каталог с кодом остаётся общим, наблюдение за ним у копии выключено.
- **Мультирепо** — к проекту можно добавить несколько каталогов (например, отдельные
  репозитории бэкенда и фронтенда): общий индекс, граф, поиск и канбан; файлы
  дополнительных каталогов ходят с префиксом «алиас/».
- **Гибридный поиск** — полнотекстовый по графу + семантический по эмбеддингам
  (Qdrant, локальная модель — без API-затрат): ИИ находит нужное, даже если
  в запросе другие слова, чем в коде и выжимках.
- **Обновления** — инкрементальный скан показывает, что изменилось (added/modified/deleted),
  переанализируются только изменённые файлы. Кнопка «Перепроверить всё» — полный пере-анализ.
- **Материалы** — загрузка записей созвонов (mp4/m4a/mp3 → локальный Whisper на GPU),
  ТЗ и документов (pdf/docx/xlsx/md/txt → извлечение текста). Из материалов ИИ делает
  выжимку и **извлекает задачи в канбан**. Документ, пришедший позже созвона, загружается
  как **уточнение**: задачи, рождённые созвоном, дополняются, а не дублируются.
- **Канбан** — Запланировано / В работе / Ревью / Готово, drag&drop. Задачу можно ставить
  как угодно длинно — короткая подпись остаётся на карточке, полный текст уходит в описание
  и целиком доходит до проработки. Готовое досье (где смотреть, нюансы, как проверить,
  развилки, файлы) копируешь одной кнопкой и вставляешь в Claude Code. ИИ управляет доской
  через MCP-инструменты: создаёт задачи, улучшает описания, помечает выполненное с отчётом.
- **RLM-проработка задач** — пайплайн выше, плюс поиск дублей и продолжений среди существующих
  задач и (по желанию) доисследование невыясненных вопросов.
- **Планировщик** — крупная задача (например, с созвона) декомпозируется: RLM-исследование
  кодовой базы → общий план → подзадачи в канбане с зависимостями «что за чем делать».
- **Наблюдение за каталогом** — включаешь галку, и правки в коде сами запускают
  инкрементальное обновление индекса (watchdog с дебаунсом).
- **ИИ-проверка «что уже сделано»** — по каждой открытой задаче ИИ ищет реализацию
  в кодовой базе и помечает выполненные с отчётом и ссылками на файлы.
- **Импорт истории git** — коммиты группируются в выполненные работы: совпадающие открытые
  задачи закрываются, частично сделанные получают галочки на шагах плана.
- **Экспорт карты знаний** — один markdown-файл: обзор, компоненты, соглашения, задачи, файлы.
- **Плагин Claude Code на проект** — MCP-сервер + скиллы (архитектура, бизнес-логика,
  рабочий процесс, разбор задач, как искать). Ставится кнопкой **только в свой проект**
  (запись в `<каталог проекта>/.claude/settings.local.json`), поэтому в остальных репозиториях
  его не видно; глобальная установка через маркетплейс осталась как вариант.
- **Два языка** — интерфейс переключается между русским и английским (cookie, без префиксов
  в URL); язык ИИ-контента — отдельная настройка бэкенда (`AI_LANGUAGE`).

## Запуск

Требуется: Docker Desktop, Python 3.13 (`py`), Node.js 20+, установленный и авторизованный
[Claude Code CLI](https://code.claude.com/docs/en/cli-reference). Вызовы ИИ идут через
подписку Claude Code, отдельный API-ключ не нужен.

```bash
git clone https://github.com/1MatrixD/Project-AI.git
cd Project-AI
cp .env.example .env        # задать POSTGRES_PASSWORD, NEO4J_PASSWORD, JWT_SECRET
```

Одной командой (поднимет docker-инфраструктуру, при первом запуске поставит зависимости,
откроет бэкенд и фронтенд в отдельных окнах и запустит браузер):

```powershell
.\start.ps1
```

Либо вручную:

```bash
# 1. Инфраструктура (Postgres 5432, Neo4j 7474/7687, Qdrant 6333)
docker compose up -d

# 2. Бэкенд (порт 8010) — миграции накатываются сами при старте
cd backend
py -3.13 -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\python -m uvicorn app.main:app --host 127.0.0.1 --port 8010

# 3. Фронтенд (порт 3010)
cd frontend
npm install
npm run dev          # порт 3010 зашит в скрипт
```

Открыть http://localhost:3010. Конфигурация — в `.env` (см. `.env.example`, там все
параметры с комментариями). Главные: `AI_LANGUAGE` (`ru` / `en` — язык ИИ-контента
и сообщений фоновых работ; язык интерфейса переключается в шапке), `AI_MODEL` и
`CHAT_DEFAULT_MODEL`, бюджет анализа (`AI_MAX_FILES_PER_RUN`, `AI_CONCURRENCY`,
`JOB_CONCURRENCY`), глубина RLM (`RLM_MAX_DEPTH`, `RLM_BRANCHING`, `RLM_MAX_NODES`).

Система рассчитана на локальный доверенный контур: бэкенд читает каталоги проектов напрямую,
диалог выбора каталога системный (Windows), Whisper работает на локальном GPU/CPU, API
слушает 127.0.0.1. На Linux/macOS работает всё, кроме `start.ps1` и системного диалога
(вместо него — встроенный выбор каталога).

## Тесты

```bash
cd backend
.venv\Scripts\python -m pytest -q
```

Интеграционные тесты гоняют весь пайплайн (индексация → граф → векторный поиск →
мультирепо → задачи → RLM-проработка → планировщик → чат → материалы → git-импорт → SSE/отмена →
watchdog → alembic-миграции → локализация) на фейковом claude-бинаре и фейковом эмбеддере — без
затрат на API. Нужны запущенные Postgres, Neo4j и Qdrant из docker compose; тесты создают
свою базу `projectai_test`.

Фронтенд: `npm run lint` и `npx tsc --noEmit` в `frontend/`.

## Тестовые проекты

В `test_projects/` — две вымышленные запутанные кодовые базы (доставка еды на FastAPI + Next.js
в двух репозиториях и прокат техники на TypeScript-монорепо), 14 задач, сформулированных так,
как их приносят из поддержки и с созвонов, и ключ проверки (`ANSWERS.md`): настоящая причина,
файлы, которые обязаны попасть в досье, и типичные ложные версии. Это не часть продукта, а полигон
для оценки: нашла ли система *настоящую* причину, а не первую похожую строчку.
См. [test_projects/README.md](test_projects/README.md).

### Результаты на сегодня

Ручная оценка автора по ключу, один прогон на задачу, модель индексации и проработки `sonnet`,
август 2026. Шкала 0–10 на задачу: названа настоящая причина, в досье есть обязательные файлы,
шаг диагностики и шаг проверки, продуктовые развилки вынесены в открытые вопросы, а не решены
молча; выдуманное утверждение снимает баллы.

| Прогон | Результат |
|---|---|
| Фикстура «Скороход», задачи 1–5, первый заход (1–2 августа) | 8, 9, 10, 10, 10 |
| Та же фикстура, все 8 задач, после того как в промпт проработки добавились развилки и последствия (2 августа, `RLM_MAX_DEPTH=2`, доисследование выключено) | 10 по каждой задаче; фича «чаевые» поднялась с 7 до 10 |
| Сам Project AI, 6 задач, поставленных автором своими словами (3 августа) | 58 / 60; два балла потеряны на одной выдумке про компонент, якобы обходящий общий API-клиент |

Ссылки на файлы и строки выборочно проверялись и оказывались точными. По задаче 4 досье нашло
два механизма, которых не было в ключе (SSE-поллинг схлопывает переходы статусов, два set_status
до одного commit), и ключ дополнен. После второго прогона ключ перестал различать, дальше мерить
надо на монорепо RentKit (задачи 9–14 пока не оценивались) или на самом проекте. Это ручная оценка
автора, а не воспроизводимый бенчмарк.

## Миграции

Схема Postgres описана моделями в `backend/app/models.py`, ревизии лежат
в `backend/alembic/versions/`. При старте бэкенда миграции накатываются сами
(`app/db.py` → `alembic upgrade head`), так что после `git pull` достаточно
перезапустить сервер. Установки, сделанные до перехода на alembic, помечаются
базовой ревизией автоматически — руками ничего штамповать не нужно.

По той же причине после `docker compose down -v` (снос тома вместе с данными) базу
нужно поднять заново: **перезапустите бэкенд**. Работающий процесс пересоздание тома
не заметит и будет ходить в пустую базу с ошибками вида
`relation "projects" does not exist`. Если перезапускать не хочется, схему можно
накатить отдельно — `alembic upgrade head` из каталога `backend`.

Своя миграция нужна, когда поменялись модели. Postgres при этом должен быть поднят:
autogenerate сравнивает модели с живой базой. Все команды — из каталога `backend`.

Сгенерировать ревизию по изменениям в моделях:

```bash
.venv\Scripts\alembic revision --autogenerate -m "короткое описание"
```

Дальше **обязательно прочитать полученный файл** в `alembic/versions/`. Autogenerate
не распознаёт переименования: колонку `foo` → `bar` он превратит в drop + add,
то есть в тихую потерю данных. Такие места переписываются руками через
`op.alter_column(..., new_column_name=...)`. Заодно стоит проверить, что в миграцию
не утекло лишнее — например, индексы, созданные вручную мимо моделей.

Применить:

```bash
.venv\Scripts\alembic upgrade head
```

Посмотреть SQL, ничего не применяя (полезно перед накатом на живую базу):

```bash
.venv\Scripts\alembic upgrade head --sql
```

Ещё: `alembic current` — на какой ревизии база сейчас, `alembic history` — вся цепочка,
`alembic downgrade -1` — откат на шаг назад. URL базы alembic берёт из настроек
приложения (`.env` в корне репозитория), в `alembic.ini` он намеренно не задаётся,
поэтому команды работают из любого каталога с активным venv.

Neo4j и Qdrant миграций не требуют: граф пересобирается индексацией, а коллекция
векторов создаётся сама и пересоздаётся при смене размерности эмбеддингов.
